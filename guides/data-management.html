Data Management

Our group’s research products are code and data. This page covers where data lives, what is backed up, how projects are organized, and what happens to data over the long term.

ImportantIs My Data Backed Up?

No. Nothing in our computing environment is backed up by default, including Hopper and your workstation. Any data that exists in only one place can be lost to a single disk failure or a mistaken rm, so anything you can’t cheaply regenerate needs a second copy somewhere else.

Three Kinds of Data

It helps to sort everything you work with into three categories, because they need different treatment.

Raw inputs are data you did not create: reanalysis products, climate model output, observational records, downloaded datasets. These are usually large, can usually be downloaded again, and should never be edited in place. Keep the acquisition step (the download script, the API query, the exact product version and access date) in the repository, so the data can be regenerated instead of copied around.

Intermediate products are what your workflow generates along the way: cleaned data, calibration output, simulation ensembles. These are often the largest and most expensive files you have. Some are cheap to regenerate and some represent weeks of compute, so note which is which in your README; that decides what needs a second copy.

Final products are what a paper depends on: the figures, the numbers in the text, and the specific outputs they were computed from. These have to be kept indefinitely, and they are what gets archived at submission.

For every file, ask what it would cost you if it disappeared tonight. If the answer is “a week of Hopper time,” it needs to exist in more than one place.

Where Data Lives

Location Backed up? Use for
Your workstation No Active analysis, code, small data
Hopper home directory No Running jobs, large intermediate output
GitHub Yes (as version control) Code and small text files; not large or binary data
Cornell Box / Google Drive Yes Data you need to keep but not compute on
Zenodo Yes, permanently Archived releases tied to a paper

Some consequences of this table:

  • Don’t use GitHub to store data. It’s version control for text, and large binary files make the repository permanently larger, since git keeps every version. If you’ve already committed a large file, tell Vivek before trying to remove it, because rewriting the history of a shared repository breaks everyone else’s copy.
  • Use Hopper for running jobs and move results off it once a project goes quiet, since nothing on it is backed up.
  • If you’re unsure what storage you have access to, ask Vivek before paying for something yourself.

Organizing a Project

Follow the meta-repository structure: code and analysis go in the repository, and models and data are linked from it by DOI or version number instead of being copied into it.

Within that structure, a few conventions make an analysis much easier to rerun:

  • Never edit raw data in place. Read it, transform it, and write the result somewhere else. A pipeline that starts from untouched inputs can be rerun; one that changes its own inputs can’t.
  • Use relative paths, set from one configurable root directory. Absolute paths like /Users/yourname/Desktop/project are a common reason someone else can’t run your code.
  • Name files so they sort correctly and can be parsed by a script: dates as YYYY-MM-DD, zero-padded numbers, no spaces. run_003_ssp585.nc works; final run (3) SSP5-8.5.nc does not.
  • Record where every dataset you didn’t generate came from, which version it is, and when you downloaded it. Sources move and get revised, and “the CMIP6 data” is not enough information to reproduce anything two years later.
  • Set and record random seeds. Most of our work involves Monte Carlo simulation, and an unseeded run can’t be reproduced, even by you.

Archiving for a Paper

At submission, the data behind a paper stops being your working files and becomes part of the publication record. The paper checklist covers the mechanics. A reader should be able to get from the archived material to your figures without contacting you.

As Open and Reproducible Research says, this includes the full simulation ensemble where feasible, and not only the subset used in the paper, so that readers can see how the subset was chosen.

Archive to a service that assigns a DOI, which for us usually means minting a Zenodo release from the GitHub repository. GitHub itself is not an archive: repositories can be deleted, renamed, or made private, and a bare GitHub URL in a data availability statement will eventually stop working. GitHub and Zenodo covers the steps and the order they have to happen in.

Retention and Ownership

Research data generated here belongs to Cornell, not to any individual (including the person who produced it, and including Vivek). This comes up in two situations: when someone leaves the group (see Leaving the Group), and when someone outside the group asks for data.

Funders set minimum retention periods. Under federal rules (2 CFR 200.334), award records must be kept for three years after the final financial report is submitted, and some awards and journals require longer. Data underlying a published paper should be kept indefinitely through its archived DOI, whatever the minimum is.

If someone outside the group asks you for data or code that isn’t public yet, please check with Vivek before sending it. We publish everything eventually; the reason to check is to make sure it goes out with the right documentation, license, and credit.

Sensitive Data

We mostly work with public environmental and model data, so this rarely comes up. When it does, these rules apply:

  • Anything involving human subjects needs IRB (Institutional Review Board) approval before any data are collected, and the approved protocol governs how the data are stored and who can see them. Talk to Vivek before starting.
  • Some datasets come with licensing or redistribution restrictions. Check before archiving, because you can’t re-release data you only had permission to use.
  • Never commit credentials (API keys, tokens, passwords) to a repository, public or private. Use environment variables or an untracked local configuration file listed in .gitignore. A key committed once stays in the history even after you delete it, so if it happens, assume the key is compromised and replace it.

If You Are Not Sure

Ask Vivek. A five-minute conversation about where to put a dataset costs much less than finding out the answer after you’ve lost it.
